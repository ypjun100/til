# 캐시 전략

- 캐시 사용시 항상 따라오는 문제로 ‘데이터 정합성’ 문제가 존재함
    - 데이터 정합성 : 데이터가 서로 일치하는 상태를 말하며, 캐시를 사용하는 경우 DB와 캐시 간의 데이터 불일치를 표현할 때 쓰이곤 함
- DB만 사용하는 환경에서는 DB에서 곧바로 조회/수정을 진행하기 때문에 데이터 정합성 이슈가 발생하지 않지만, 캐시라는 DB를 둠으로써 데이터 이중화가 발생하여 데이터 불일치 현상이 발생함
- 따라서, 적절한 캐시 읽기 전략과 캐시 쓰기 전략으로 데이터 불일치 문제를 극복해야 함

### 데이터 읽기 전략

**[Look Aside 패턴]**
![image.png](https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2F2i45c%2FbtrQOQ1Fefc%2FAAAAAAAAAAAAAAAAAAAAAPVOMrANVSrYXGsO3PcmEN_timH_hHPKDlN_VJRVJF3y%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1788188399%26allow_ip%3D%26allow_referer%3D%26signature%3DEvP7c2T57urm8NI56ZyJ8kdpq0Q%253D)

- 데이터 조회 시 먼저 캐시에 저장된 데이터가 있는지를 확인하는 전략으로, Cache Aside라고도 불림
- 반복적인 읽기가 많은 호출에 적합하며, 캐시와 DB가 분리되어 가용되기에 캐시 장애 대비 구성이 가능
    - 만약 캐시 DB에 장애가 발생해도 DB로부터 데이터를 가져올 수 있음
- 대신 캐시에 붙어있던 커넥션이 많았다면, 캐시가 다운된 순간 순간적으로 DB로 몰려서 부하 발생 가능
- 캐시와 DB 간의 정합성 문제가 발생할 수 있으며, 초기 조회 시 무조건 DB를 조회해야 함
    - 따라서, 데이터의 종류가 다양한데 각 데이터가 한 번씩 조회되는 서비스라면 비효율적임

> ‘Look Aside’라는 이름은 애플리케이션이 데이터를 조회할 때 곧바로 DB로 가지 않고, 먼저 옆에 있는 캐시를 슬쩍 들여다본 뒤 없으면 DB로 가는 동작 방식에서 유래했다.

**[Read Through 패턴]**
![image.png](https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2FekuWqE%2FbtrQPeuqqV0%2FAAAAAAAAAAAAAAAAAAAAAAORHHVl2iu8s_l4D6Bmyr5Sx690aXe0gIi2yoQGWIaK%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1788188399%26allow_ip%3D%26allow_referer%3D%26signature%3D1i1XKWMdJLVq6xbPZccikrnisIY%253D)

- 캐시에서만 데이터를 읽어오는 전략으로 Look Aside와 비슷하지만 데이터 동기화를 라이브러리 또는 캐시에게 위임하는 방식임
- 캐시와 DB 간의 데이터 동기화가 항상 이루어져 데이터 정합성 문제에서 벗어날 수 있음
- 반면 데이터를 조회하는데 속도가 느려지며, 데이터 조회를 캐시에만 의지하기에 SPOF가 발생함
    - SPOF를 극복하기 위해 캐시 서버를 Replication 또는 Cluster로 구성하여 가용성을 높임
- 보통 읽기가 대부분인 워크로드에 적합함

> Read Through나 아래서 설명할 Write Through와 같이 ‘Through’ 전략들은 DB에서 해당 기능을 제공하는지가 중요하다.

### 캐시 쓰기 전략

**[Write Back 패턴]**
![image.png](https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2Fbx8ccX%2FbtrQOQsNl1R%2FAAAAAAAAAAAAAAAAAAAAAFS7V2DTH9wOUwxqEdvcTUMdk9NQIVHwDDXhOYOBaT5M%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1788188399%26allow_ip%3D%26allow_referer%3D%26signature%3Dx6fMGcmV7agEW5NJFlgs8HvUnq8%253D)

- 데이터를 저장할 때 DB에 바로 쿼리하지 않고, 캐시에 모아서 일정 주기의 배치 작업으로 DB에 반영
- Write Behind 패턴이라고도 하며, 캐시와 DB 동기화 작업을 비동기적으로 수행하게 됨
- 쓰기 작업을 캐시에 모아놨다가 한 번에 DB에 쓰기 때문에 쓰기 쿼리 비용과 부하를 줄일 수 있음
    - 따라서, 쓰기 작업이 빈번한 서비스에 적합함
- 하지만 캐시에 장애가 발생하면 DB에 반영되지 않은 데이터는 영구 소실될 수 있음

**[Write Through 패턴]**
![image.png](https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2FDLlbo%2FbtrQT53hVhs%2FAAAAAAAAAAAAAAAAAAAAAKlKX191C3ZbB-mOzA2pn1Tw-gqo9q7UkGGUFOrYwG9p%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1788188399%26allow_ip%3D%26allow_referer%3D%26signature%3DW8JDyHrz%252BZRqO4twBJ4btxBU%252Bbo%253D)

- DB와 캐시에 동시에 데이터를 저장하는 전략으로 먼저 캐시에 저장한 다음에 바로 DB에 저장함
    - Write Back 패턴과 달리 캐시에 쓰기들을 모아두는 방식이 아닌 바로 DB에 저장하는 방식임
- Read Through 패턴과 마찬가지로 DB 동기화 작업을 캐시에게 위임하는 방식
- DB와 캐시가 항상 동기화 되어있어, 캐시의 데이터는 항상 최신 상태로 유지하게 됨
    - 따라서, Write Back과 달리 캐시에 장애가 발생해도 비교적 데이터 유실이 적음
- 매 요청마다 두 번의 쓰기가 발생하게 되기에 빈번한 생성/수정이 발생하는 서비스에는 비효율적임

> Write Through 패턴과 Write Back 패턴 모두 자주 사용되지 않는 데이터도 캐시에 저장되는 리소스 낭비가 발생하기에 이를 해결하기 위해 TTL을 꼭 사용해줘야 한다.

**[Write Around 패턴]**
![image.png](https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2FbczXKV%2FbtrQTWMk5OZ%2FAAAAAAAAAAAAAAAAAAAAAEaILgblNyYNkc4LPTO1KRlaJlJ25eUmT5tZ1LN5irQi%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1788188399%26allow_ip%3D%26allow_referer%3D%26signature%3Dx7FnIBw380DqZOkrg5UJy5jZT98%253D)

- 데이터를 저장할 때 오직 DB에만 저장하는 방식 (캐시에 데이터를 저장하지 않음)
    - 캐시는 데이터를 조회할 때 캐시 Miss 상황에서만 저장됨
- 캐시를 직접 갱신하지 않기에 Write Through 보다 빠르지만, 데이터 정합성 문제가 쉽게 발생함
    - 따라서, DB 데이터 수정/삭제 시마다 캐시 또한 반영하거나 TTL을 짧게 조정해줘야 함

> Write Around는 동작 방식 그대로 쓰기 작업 시에 캐시를 우회(By-Pass)하기 때문에 Around라는 표현이 붙었다.

### 캐시 읽기 + 쓰기 전략 조합

**[Look Aside + Write Around 조합]**
![image.png](https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2FdAFVj1%2FbtrQSXSKf6Y%2FAAAAAAAAAAAAAAAAAAAAAGkeKZBqdb6cvocyt-yXDKbbz1w2hGP5YBjZK5Kx_6Je%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1788188399%26allow_ip%3D%26allow_referer%3D%26signature%3DUDkhZmChdYubxHtW63Vi0rTKfFo%253D)

- 읽기 시에는 Look Aside 방식대로 요청이 오면 캐시 확인 후, 없으면 DB에 조회한 뒤 결과를 캐싱함
- 쓰기 시에는 Write Around 방식대로 데이터 저장/수정 삭제 시에 캐시를 건드리지 않고 DB에 반영함
- 캐시와 DB가 분리 운영돼 캐시가 다운돼도 서비스 자체는 DB로 폴백하여 장애 대응력이 좋음
- 쓰기 시 캐시를 갱신하지 않으므로 데이터 정합성 문제가 발생할 수 있음
- 한 번 쓰고 자주 읽지 않는 데이터에 적합하며, 반복 조회가 많은 워크로드에 적합함

**[Read Through + Write Around 조합]**
![image.png](https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2FdBO0Su%2FbtrQPeH3N5B%2FAAAAAAAAAAAAAAAAAAAAAGoGAwQfheCnl-TvLxCSC1njd0kqil_mFH9isBx790bZ%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1788188399%26allow_ip%3D%26allow_referer%3D%26signature%3D5rNG6sbelF0JCQc6ib6kcDANfi0%253D)

- 읽기 시에 앱은 항상 캐시에만 요청을 보내고, 캐시 스스로가 DB를 조회해 데이터를 채운 뒤 반환함
- 쓰기 시에 데이터는 항상 DB에만 직접 저장하고, 캐시에는 데이터를 저장하지 않음
- 캐시를 조회할 때 항상 DB에서 최신 데이터를 먼저 가져오기에 데이터 정합성 이슈를 줄일 수 있음
    - 이를 만족하려면 데이터 수정 시에 캐시 Invalide나 TTL을 짧게 조정하는 등의 조치가 필요함
- 한 번 쓰고 잘 안 읽는 데이터(실시간 로그 등)에 효율적임

**[Read Through + Write Through 조합]**
![image.png](https://img1.daumcdn.net/thumb/R1280x0/?scode=mtistory2&fname=https%3A%2F%2Fblog.kakaocdn.net%2Fdna%2FbV9ao2%2FbtrQRnqEAV8%2FAAAAAAAAAAAAAAAAAAAAAFxt3rTjEDMwevwJ0y15JALlpva7jHlJgXEQnO8WjiYR%2Fimg.png%3Fcredential%3DyqXZFxpELC7KVnFOS48ylbz2pIh7yKj8%26expires%3D1788188399%26allow_ip%3D%26allow_referer%3D%26signature%3DsQfWz%252BDQgtVBYKPkTSdXO0%252FfK8A%253D)

- 읽기 시에 앱은 캐시만 바라보고, 캐시 미스 시 캐시가 자동으로 DB에서 데이터를 가져와 채움
- 쓰기 시에 데이터를 저장/수정할 때 캐시와 DB에 동시에(혹은 캐시를 거쳐 DB로) 반영함
- 모든 DB 쓰기가 캐시를 통해 이루어지기 때문에 데이터 정합성이 자동으로 보장됨
- 은행/결제 시스템처럼 데이터 정합성이 중요한 도메인에서 사용됨
