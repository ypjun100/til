# 도커 스웜 모드와 쿠버네티스 간의 비교

### 모든 리소스는 오브젝트 형태로 관리됨

- 쿠버네티스 오브젝트는 리소스마다 원하는 상태를 저장하며, 쿠버네티스는 해당 상태를 실제 상태와 싱크함
	- 하나의 오브젝트는 하나의 `spec`과 `status`를 지속적으로 비교해 실제 상태를 원하는 상태로 맞춰감
	- `spec` : 사용자가 오브젝트에 원하는 상태를 정의하는 명세
	- `status` : 컨트롤 플레인이 갱신하는 오브젝트의 현재 상태
- 쿠버네티스는 컨테이너의 집합(Pods), 이를 관리하는 컨트롤러 등 아래의  하나의 오브젝트로 사용 가능함
- **오브젝트 예시**
	- **Pod** : 컨테이너 하나 이상을 묶은, 실행되는 최소 단위
	- **Service** : 유동적인 파드 IP 대신 안정적인 접근을 제공하는 로드밸런싱 단위
	- **Volume** : 파드가 사라져도 데이터를 보존할 수 있게 하는 스토리지
	- **Namespace** : 클러스터 내 리소스를 논리적으로 구분/관리하는 그룹

### 쿠버네티스는 보통 YAML 파일을 주로 이용함

- 쿠버네티스에서는 `kubectl` 명령어를 사용하며, 대부분의 작업은 해당 명령어로 진행할 수 있음
- 스웜 모드에서 스택을 생성하기 위해 YAML 파일을 사용한 것처럼 쿠버네티스도 가능함
- 특히 쿠버네티스에서는 컨테이너 뿐만 아니라 모든 리소스 오브젝트를 생성/삭제하는 데 사용함
	- 쿠버네티스에서 실제 서비스를 배포할 때에도 여러 개의 YAML 파일을 정의해 적용하는 방식을 사용함

### 쿠버네티스는 여러 개의 컴포넌트로 관리됨

- 쿠버네티스 클러스터 내의 노드의 역할은 크게 마스터 노드와 워 노드로 나뉘어져 있음
	- 마스터 노드는 쿠버네티스가 동작할 수 있게끔 클러스터를 관리하는 역할을 담당
	- 워커 노드에는 실제로 애플리케이션 컨테이너가 생성됨
- 쿠버네티스는 클러스터를 관리하기 위해 아래와 같은 여러 종류의 컴포넌트들이 동시에 실행됨
	- 마스터 노드에서는 클러스터를 관리하기 위한 API 서버, 컨트롤러 매니저, 스케줄러 등이 실행됨
	- 모든 노드에서는 오브레이 네트워크 구성을 위한 프록시와 네트워크 플러그인이 실행됨
	- 또한, 모든 노드에는 마스터/워커 노드 간의 통신 역할을 담당하는 kubelet 에이전트가 실행됨
